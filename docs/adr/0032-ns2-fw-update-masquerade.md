# 0032 — 手柄固件更新的伪装应答与版本固化

- 状态: active
- 日期: 2026-09-15
- 替代: 无

## 背景

Switch 2 主机（系统 23.0.0，实机抓包）会给手柄推固件更新：菜单里的更新推送由 Command 0x0d 驱动，数据经 0x0018 以记录流推下（实测 114 帧、4751 条记录、483,692 字节），收尾各有指令。本设备是模拟手柄，没有可升级的固件，原实现只把数据收下并在静默 10 秒后递增上报版本——没有帧应答，主机推完一帧就停住报通信中断；补上收尾重启后更糟：主机会把重启当成更新没生效而重推整包，形成推包与重启的循环。

## 决策

按「接住数据、逐帧应答、不重启」处理：0x0018 的记录流在 target/ns2/ns2_upgrade.c 里按帧装配（帧长取帧头字节 4-5 的大端值），帧凑齐即按指令通道的同一套格式回一条应答（默认空体，fwack 可现场换体，实机验证空体即可让主机推完全包）；收尾的 0x0d/0x07 默认不重启，重启改由串口 fwapply on 一次性武装，只用于对照实验；上报给主机的固件版本固化在 config/app_config.h 的 CONFIG_DEFAULT_FW_VERSION_*，串口 fwver 可临时覆盖。

## 考虑的方案

- 收下数据后递增上报版本（原实现）：主机推完一帧就停、报通信切断，更新提示照旧，等于没解决问题
- 收完重启伪装成真机刷完重启：主机会把控制器重启判成更新没生效并重推整包，实测形成推包与重启的循环
- 整包收完再回一条带版本号的应答：帧体语义未逆向（高熵、像加密或压缩），无法确定主机期待的载荷

## 影响

- 菜单里的更新能把整包推完，链路不掉、也不再有重启循环；但主机最终仍报一次通信中断，因为我们不会带着新版本回来。
- 更新提示由固化版本决定：抬到 9.9.9 后主机不再弹提示（菜单里仍可手动推），但**是否根治未确认**——
  主机认的版本号未知（帧体未解）、收尾那次通信中断仍在，继续根治需要解出帧体或拿到主机期望的版本号。
