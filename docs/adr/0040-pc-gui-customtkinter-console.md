# 0040 — PC 侧新增图形界面入口：CustomTkinter 连接控制台

- 状态: active
- 日期: 2026-09-16
- 替代: 无

## 背景

PC 侧工具 pc/remapadctl.py 的交互模式把命令输入与设备输出挤在同一个终端流里：固件日志一边滚动，命令一边敲，翻历史与对账全靠眼睛。
实机验收里反复出现的动作（开连接窗口、配新主机、唤醒、截图、升级）每次都要手打一整行命令，参数记错就白跑一趟。
设备只有一根 Type-C，串口同时承载桥接帧、固件日志与 CLI 文本，PC 侧只能有一个持有者，界面不能另起进程去抢同一个口。
会话循环、OtaJob、ShotCollector 与命令分发早已集中在 remapadctl.py，缺的只是一层把输入输出接到图形控件的适配。

## 决策

新增图形界面入口 pc/remapadgui.py，用 CustomTkinter（Tk 8.6）搭界面；界面与命令行共用 remapadctl.py 的 Session 与 link.py 的串口实现。
Session 的输出改走可注入的 Reporter：line / error 写一行文本，event 报手柄接入、截图落盘、升级进度与链路错误；命令行实现保持写标准流，界面实现写队列。
界面只做三件事：把队列排空后写进日志区、把按钮与输入框里的命令塞进同一个 Session.commands 队列、把事件映射到状态灯、进度条与系统看图器。
会话主循环固定在工作线程里跑（1 ms 轮询与转发节奏不变），Tk 主线程只跑 mainloop 与 40 ms 的队列排空；按钮、开关与关窗只改共享状态。
端口枚举读注册表的 SERIALCOMM 键，界面不引入 pyserial 与 Pillow：截图落盘后用系统看图器打开，镜像仍在本地先校验再推送。
依赖 customtkinter 写进 pc/pyproject.toml 与 uv.lock；入口沿用 link.py 的 Windows 限制。

## 考虑的方案

- 界面里再实现一份转发与升级（否决：串口只有一个持有者，转发、截图与 OTA 的实现会立刻分叉）
- 界面起子进程包住命令行并解析 stdout（否决：进度与失败判定要靠解析给人看的文字，脆弱且拿不到结构化事件）
- 把会话循环放进 Tk 的 after 轮询（否决：Tk 定时器精度跟不上 4 ms 的转发节奏，手柄报告会在 HID 缓冲里堆积）
- 引入 Pillow 在窗口内直接显示截图（否决：为一个 240×280 的调试图加一份二进制依赖，系统看图器已经够用）

## 影响

- 正面：常见验收动作变成一次点击，命令与日志各归其位，历史命令可以回溯；命令行与界面共用同一份会话实现，行为不会分叉。
- 正面：界面复用 Reporter 与 Session，主机端用例可以覆盖端口枚举、镜像校验、帧编解码与输出分流，不必启动窗口。
- 成本：pc/ 多一个入口与一份界面代码，依赖多一个 customtkinter（连带 darkdetect 与 packaging）；会话新增输出必须走 Reporter，直接 print 的内容不会出现在界面上。
- 限制：界面与命令行不能同时连一个口；界面不做自动连接、不写配置文件；升级会让会话随设备重启结束，等设备回来自动重连是可选项。
