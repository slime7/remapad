# 0045 — 主机输出原始采集经桥接帧回传 PC

- 状态: active
- 日期: 2026-09-20
- 替代: 无

## 背景

主机下发的震动、玩家灯、触觉采样与音频等输出，目前只有两条被消化的去向：解析成结构化事件驱动反馈，或按输入设备布局重新编码写回手柄。
协议对账（玩家灯掩码、0x0A 采样流、复合输出前缀、主机更新记录流）只能靠逐条 ESP_LOGI 留痕。
日志刷屏会拖住 NimBLE 主机任务，采样等热路径命令已经被迫只按秒聚合。
需要一条不占日志通道、能按需开关的抓包通路，把布局解析之前的最原始数据交给 PC 侧落盘分析。
串口 CLI 与桥接帧共用一根 USB-Serial/JTAG 是现成的传输面。

## 决策

在 ble_controller 的 GATT 写分发入口（解析之前）加采集钩子。
原始字节按通道字节（controller.md GATT 表句柄低字节）拷进 `dp/dp_capture` 的环形队列，数据面任务每拍排空并经新桥接帧 0x12（HOST_RAW）回传 PC。
帧载荷是通道 + 标志/长度（bit7 截断）+ 最多 253 字节原文，帧头 slot 带设备侧记录号供 PC 检测跳号丢包。
采集默认关闭，串口 `capture on|off` 开关。
PC 侧 remapadctl 用 `--capture`（`--seconds` 控时长）与交互命令 `:capture <路径>|off` 接住落盘成文本，与手柄转发同会话共存。
单条写入超过 253 字节截断并带标记；队列满丢弃新到的记录，不覆盖已排队数据。

## 考虑的方案

- 主机输出解析点（ble_session）里逐事件留痕进日志：零新增帧，但文本日志与 CLI 共用发送环、热路径必须限频，等于回到现状的刷屏与丢包问题（否决）
- 复用 FEEDBACK 帧扩展字段带原文：FEEDBACK 语义是归一化后的持续帧（写回语义变化才发），塞原始字节会破坏「变化才发」的去重语义且载荷放不下 32 字节参数包之外的指令流（否决）
- 独立诊断帧 0x12 + 设备侧环形队列 + 显式开关（采纳）：与反馈帧同一投递约束（BLE 回调不做串口传输），开关保证不开时不占串口，记录号让丢包可见

## 影响

- 正面：玩家灯、震动参数包、采样流、复合输出与固件更新记录流都有逐包原文可对账，PC 侧拿到的是带相对时间与通道名的文本，协议排查不再依赖日志限频下的残片。
- 代价：多占约 3 KB 内部 RAM（12 条记录环）与一条新帧类型。
- 开启时震动流约 66 帧每秒持续占串口，因此默认关闭、由用户显式打开。
- 主机输出长块（升级数据）只留前 253 字节，完整记录流仍以 ns2_upgrade 的装配结果为准。
