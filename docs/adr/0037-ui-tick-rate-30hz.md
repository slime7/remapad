# 0037 — PocketJS UI 帧节奏改为 30 Hz，与帧绑定的时长按公共变量换算

- 状态: active
- 日期: 2026-09-16
- 替代: 0017

## 背景

60 Hz tick 下，静止帧的 guest turn 实测约 5.7 ms，占满一帧 16.7 ms 预算的三分之一，且与画面是否变化无关。
这段开销来自每帧重建 draw list、跑一遍 Vue 响应式与软件 RGB565 光栅化（见 0017 的实测）。
同优先级的 remapad-dp 数据面任务（5 ms 一拍，手柄经 NS2 编到 BLE 上报）与 BLE、USB 栈共享同一颗 CPU，空转的那三成算力挤的是上报节拍的余量。
界面以列表、开关与静态卡片为主，触摸与手柄在屏幕上的按键都只用于测试，取样粒度变粗不影响实际观感。
设备侧没有运行时帧率档位：节奏由 host profile 的 tickHz 与 bundle 的烘焙值共同决定。

## 决策

host profile（firmware/pocket.host.json）的 tickHz 定为 30。
UI 侧新增 ui/src/tick.ts 作为帧节奏的唯一来源：TICK_HZ 取框架烘焙的 TICKS_PER_SECOND，真机 mount 时框架断言它等于固件声明的 ui.__tickHz。
该模块另导出 TICK_MS、SECOND_TICKS、ticksForMs、msForTicks 与 ticksForStepAt60Hz。
与帧绑定的取值分两种写法，实际帧数都由 TICK_HZ 算出。
时长（状态轮询间隔、帧率采样窗口、uptime 推算、操控提示停留、调试页高亮）写成毫秒，经 ticksForMs 换算。
帧步进（配对页 spinner）沿用 60 Hz 下的 frameStep 3 帧，经 ticksForStepAt60Hz 换算后取整到整数帧：30 Hz 下是 2 帧，每张图稳定停留 67 ms。
小数帧不按累计帧推进：那会让相邻两张图的停留时长在 33 ms 与 67 ms 之间跳，转速忽快忽慢。
浏览器预览页从预览服务器的 /host-profile.json 读同一份 tickHz 驱动帧循环，不再写死 60。

## 考虑的方案

- 30 Hz tick（选定）：静止帧每秒的 turn 开销从约 340 ms 降到约 170 ms，取样粒度 33.3 ms，触摸与手柄在屏幕上仍逐帧可用。
- 保持 60 Hz（否决）：静止画面每秒约三分之一核被 UI 占用且没有任何画面变化，数据面上报的抖动余量更小。
- 只把固件帧循环放慢、bundle 仍按 60 Hz 烘焙（否决）：框架在 mount 时断言烘焙值等于宿主声明值，虚拟时钟也按烘焙速率推进，静默放慢会让动画时长与 uptime 推算整体错位。
- 做成运行时帧率档位（否决）：节奏与字形密度同性质，是关键帧时间轴与动画衰减常数的换算基准，不做运行时切换。
- 帧步进保留小数帧（否决）：整圈时长能与 60 Hz 时期一致（12 帧 = 0.4 秒），代价是相邻两张图的停留时长在 33 ms 与 67 ms 之间交替，转速看上去忽快忽慢。
  整圈差 100 多毫秒看不出来，不连贯看得出来。

## 影响

- 静止帧的一帧预算从 16.7 ms 放宽到 33.3 ms（turn 约 17%），每秒省下约 170 ms 的 CPU 交给数据面与协议栈。
  整幅重绘帧（渲染约 50 ms 起）依旧由渲染成本定拍，目标帧率调低不会让滚动变快。
- 触摸与手柄在 UI 侧的取样粒度从 16.7 ms 变为 33.3 ms，短于一个 UI 帧的点按在 guest 眼里不存在。
  手柄链路本身（数据面 5 ms 采样、15 ms 上报）不经过 UI 帧，不受影响。
- 与帧绑定的取值统一走 ui/src/tick.ts：改 profile 的 tickHz 后重新编译前端并重建固件即可。
  计时器与提示的墙钟时长不变，帧步进取整到整数帧、整圈时长允许偏差（spinner 从 0.4 秒变 0.53 秒）。
  端到端测试台按应用帧计数，预览页帧率随之变成 30 FPS。
