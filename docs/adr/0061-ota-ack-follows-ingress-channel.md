# 0061 — OTA ACK 跟进帧通道单路回发

- 状态: active
- 日期: 2026-09-30
- 替代: 无

## 背景

0060 把 OTA 统一到串口与 WiFi 双通道时，定下 ACK 按在位通道双路回发。
现实链路里「串口线插着」不等于「COM 口有人打开」：USJ 的连接状态分不出这两种。
WiFi 升级时每条 ACK 都先在串口发送环上白等满预算，窗口往返被抬到与窗口超时同量级。
整窗重发放大流量后设备端应答队列积压丢弃，升级吞吐跌到不可用。

## 决策

ACK 改为跟进帧通道单路回发：从哪个口收到升级帧，应答就从哪个口出去。
进帧通道在 ota_link 适配层按帧标记，会话核心、协议帧与 PC 状态机不动。
出口不在位时丢弃该条应答，由 PC 端窗口超时整窗重发兜住，会话照常推进。
配套把 netlog 会话期间的 WiFi 省电关掉（会话开启时设 WIFI_PS_NONE），PC 端窗口应答超时相应收紧。

## 考虑的方案

- 保留双路回发，只缩短串口应答的等环预算（否决：串口升级的应答可靠性靠这笔预算兜日志挤占，收窄会在真串口上丢应答）
- 保留双路回发，由设备识别 COM 口是否真的被打开（否决：USJ 驱动给不出这个判据，自造状态跟踪引入新的不可靠源）
- 只调 PC 端窗口超时与窗口大小（否决：往返下限卡在设备端 ACK 出口，参数调不出数量级）

## 影响

- 正面：WiFi 升级往返不再为死串口付费，配合省电关闭与收紧的窗口超时，吞吐恢复到接近串口的量级。
- 串口升级行为不变：没有 UDP 流量时 ACK 照旧走 USJ。
- 串口监视与 WiFi 工具并存的场景里，非进帧通道不再收到 ACK 帧（日志与 CLI 抄送不受影响）。
