# 0017 — 显示通路取值、行带刷新与滚动帧的性能边界

- 状态: active
- 日期: 2026-09-13
- 替代: 无

## 背景

实机滚动明显卡顿。用临时探针（每帧把可见页面的内容列平移 3 px，等价于滚动帧的重绘负载）配合固件每 5 秒的帧统计做实测：整屏 240 × 280 = 6.72 万像素的位移帧在树中只有当前页时约 61 ms、七个页面常驻时约 90 ms（11–16 fps），静止帧 5.7 ms、稳定 60 Hz。逐项标清过根背景、strip 缓冲位置（PSRAM 与内部 RAM）、条带高度（32 行与 140 行）与 SPI 时钟（40 与 80 MHz）：滚动帧成本与这些取值基本无关，说明开销在 PocketJS 每帧重建 draw list 与软件 RGB565 光栅化本身——实测该光栅约 0.5–0.65 µs 每像素，其中本机加速器只占约 0.01（填充）与 0.13（掩码混合）µs 每像素，其余在渲染器的掩码构建、字形图集与纹理采样上（预置归档，应用侧不可改）。

同一时期实机还出现过画面竖条与错行内容，根因有两条：SPI2 的 80 MHz 超频，以及条带窗口窄于视口时漏做逐行压缩（x = 0 的窗口同样需要压缩）。

## 决策

1. 面板 SPI2 取微雪例程的 40 MHz。传输在条带管线里基本被渲染盖住（每帧实测等待 DMA 不足 2 ms），不构成瓶颈；80 MHz 会破坏窗口命令期的时序裕量。
2. strip 缓冲改成 32 行高的条带（3 条共 45 kB，优先内部 RAM，要不到时退回 PSRAM）；窗口窄于视口时按行压缩成紧凑布局，字节序交换由面板传输统一负责。
3. 渲染器的加速回调由本机整数实现接管（`firmware/main/render_accel.c`，S3 没有 PPA）：填充、A8 掩码混合与 PSM5650 直拷三条路径，阈值 `min_*_pixels` 放到 1；整行全透明/全不透明的掩码行走整行快路径。
4. 不做字段切分，整幅在一帧内刷完：damage 折成 32 行高的行带表，本帧的每条行带都在本帧内按绝对行序自上而下渲染并提交，画完一条清一条。曾按隔行思路试过每帧只刷相位匹配的一半（`REMAPAD_FIELD_STRIDE = 2`，重帧才切分）与三分之一，实机滚动时相邻行带相差一帧的位移在文字与圆弧上呈现明显纵向错位，观感不可接受，因此放弃；整幅顺序刷新每帧只留一个撕裂边界。
5. 面板提交改异步：`panel_transfer_async` 只入队并交回完成序号，调用方按 strip 槽等待该槽上一笔传输结束，渲染与 DMA 因此可以重叠。
6. 滚动位移每帧走官方 `jump` + 内容节点 `nodeRef`，不走响应式绑定（官方把「信号写入 → 副作用重跑 → JSX 绑定 → 原生属性」标为毫秒级）。
7. 面板字节序转换在面板侧统一做，且必须**逐像素**换序：批量路径用 `panel_byteswap_pair()`（32 位整字内两个 RGB565 各自换字节序），不能用 `__builtin_bswap32`——后者会连同相邻两个像素的前后顺序一起颠倒，实机表现为文字发糊、圆弧与进度条边缘上下波动（平坦色块看不出），启动画面也受影响（它走同一条传输通路）。`panel_init()` 里的自检会在启动时比对批量实现与逐像素参考实现，不一致直接报错。

## 考虑的方案

- 40 MHz（选定）/ 80 MHz（试过，实机竖条，回退）
- 隔行比例 1/2（试过并否决）：实测滚动帧周期 33 ms（30.0 fps），但实机相邻行带相差一帧的位移在纵向细节上呈梳状错位
- 隔行比例 1/3（试过并否决）：实测滚动帧周期 26.5 ms（37.7 fps），错位比 1/2 更明显
- 整幅顺序刷新（选定）：每帧把所有行带画完，静止帧仍 60 Hz，整幅 240 × 280 帧的渲染实测约 50 ms
- 整屏单条 strip 放 PSRAM（否决）：渲染写入受 PSRAM 带宽拖累
- 保持每帧整屏重画（否决）：滚动只有 11–16 fps，且面板 40 MHz 下整帧传输本身就占 27 ms
- 应用侧压缩每帧像素之外的策略（如按帧耗时动态调整行带数量、场景化的降帧刷新）：留待确有需要时再评估，当前固定行为更可预测

## 影响

- 实测（32 行条带、整幅顺序刷新、七个页面常驻、SPI2 40 MHz）：静止帧 `avg_turn_us` ≈ 5.7 ms、`avg_render_us` ≈ 0.3 ms（damage 0），稳定 60 Hz；整幅 240 × 280 帧的渲染实测约 50 ms（启动首帧 `max_render_us`），据此滚动帧约 17–20 fps，低于隔行的 30 fps。实机滚动的手感仍优于隔行版本：慢速拖动与点击不再有纵向错位，代价集中在快速甩动时一条移动的撕裂边界。
- 帧预算的剩余大头仍是渲染器内部的掩码/图集/纹理采样（随 damage 面积线性增长）与每帧 draw list 重建；应用侧能动的只有「每帧画多少像素」，隔行曾是唯一的提速手段，代价是纵向错位。
- 撕裂：整幅顺序刷新每帧只有一个撕裂边界（画面上下两段相差一帧的位移）。要彻底消除需要面板 TE 同步或框架侧的增量刷新。
- 要达到 60 Hz 滚动需要框架侧的增量刷新（render-to-texture）或 ESP32-P4 的 PPA 硬件路径，应用侧调参覆盖不了。
- 面板输出通路的正确性用临时抓帧通路核对过：把条带像素（压缩后、字节序交换前）按窗口位置拼回整屏 dump 成 PNG，条带边界无错行、字形清晰。该通路比较的是换序**之前**的缓冲，挡不住换序自身的错误：当日实测就漏掉了「批量 32 位整字把相邻像素顺序也颠倒」这一项（根因与修法见决策 7），现在由 `panel_init()` 的启动自检兜底。
- 七个页面常驻会让每帧 draw list 更大（切页只翻 `hidden`，见 [0016](0016-mount-all-pages-before-first-frame.md)）；新增常驻页面或加大页面节点数前先评估这笔开销。
