# 0039 — 只模拟 Pro Controller 2：移除 JoyCon 形态

- 状态: active
- 日期: 2026-09-16
- 替代: 无

## 背景

实机对账确认两件事：主机只接受 public 地址的广播（派生静态随机地址在主机侧完全看不见），而一台控制器只有一个 public 地址；一把 Joy-Con 要单独配对就必须有自己的一条 public 地址。因此左右两只 JoyCon 无法在同一块板上各自寻址：共用同一地址时主机只维持一条 ACL，界面里出现两只、实际只连一只，握把页的 L+R 组合确认永远凑不齐两侧。单只 JoyCon (L) 形态虽已配通（专用通道 UUID、0x07 报文体、导轨键确认都对齐真机），但产品面需要的是「一只完整手柄」，半只 JoyCon 的按键布局与功能都不足以作为对外形态。

## 决策

设备对外只模拟一台 Pro Controller 2，JoyCon 形态整体移除：ns2_identity_t 只保留 NS2_ID_PRO；BLE 只注册 Pro 的专用输入通道 UUID（0x000E）；报告编码只保留 0x09（蓝牙）与 0x05（USB）；会话与广播回到单身份、单连接、单实例；控制面（串口 ctrl/side/rails/cmd13、bridge 的 setControllerConfig 类型字段与 pressLr 命令、UI 的手柄形态选择与左右信息行）同步收敛为「Pro + 配色」。协议事实（JoyCon 的 UUID、0x07 / 0x08 报文体、导轨键确认、四段配色）保留在 controller.md 备查。凭证与出厂块仍按身份分槽存储，将来再加型号时不必改存储与广播层的分槽方式。

## 考虑的方案

- 移除 JoyCon 形态、只留 Pro（采纳）：产品面只有一种手柄，代码与文档里的形态分支全部删掉
- 保留 JoyCon 形态但默认关闭（否决）：形态代码与两套报文体继续留在固件里，调试面与文档都要维护一条用不上的路径
- 两块板各扮一只 JoyCon（否决）：能凑成一对，但需要用户准备两块板卡，超出本产品的目标形态

## 影响

- 正面：设备行为单一可预期（单身份、单连接、单报告格式），专用输入通道与报文体只剩一条，主机侧不会因为型号错配停在「待确认」；控制面与 UI 少掉一整类状态，文档与用例同步收缩（固件主机端用例从 151 条降到 142 条）。
- 约束：物理 Joy-Con 作为输入设备时不再有对应的输出身份，其报文体走解析重编码路径（0x07 载荷不投给 0x09 会话），按键按布局映射进 Pro 报文；透传的身份条件因此去掉，只按报告格式与目标语言判断（部分取代 ADR 0026 里的身份约束）。
- 后续：若将来要在同一块板上再上线第二种形态，需要的不是代码而是第二个 public 地址（另一块芯片或控制器侧的地址分身能力），届时按本 ADR 的分槽结构重新评估。
