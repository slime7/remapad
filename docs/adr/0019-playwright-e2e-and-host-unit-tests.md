# 0019 — 以端到端与主机端测试作为回归基线

- 状态: active
- 日期: 2026-09-13
- 替代: 无

## 背景

项目的快速迭代集中在 UI 行为与固件协议编码上：UI 侧页面切换、滚动动能与触摸命中规则多次修改，固件侧 NS2 报告编码、序列号校验位与像素加速回调都只能靠真机肉眼验证。真机验证一次要烧录、要人手点击，代价高且不可重复，同一类缺陷会反复出现；UI 的回归尤其难发现，因为改一处布局可能让另一页的滚动或点击失效，而预览页本身没有自动化手段。

## 决策

建立两条开发机上的回归基线。UI 侧用 Playwright 驱动现有的触摸预览页（与 pnpm run dev 同一页面与同一官方 wasm 渲染核心，输入统一为触摸），通过探针接入官方 DevTools 通道取得组件树与边界命中，断言分三层：组件树语义事实、屏幕像素（区域指纹与取样点）、预览页读数；固件侧把与硬件无关的纯逻辑模块（ns2_report、ns2_serial、ns2_frames、render_accel、dp_source）用开发机编译器编译成可执行文件运行，ESP-IDF 环境头文件以最小替身补齐，被测源码保持为真源码。两条基线都规定：修 bug 前先写一条能复现的用例，用例转绿才算修完。

## 考虑的方案

- 使用 ESP-IDF 自带 Unity + pytest-embedded 在真机上跑测试（否决：每次都要串口与真板，改一行也要等烧录，无法作为日常回归网）
- UI 侧另写一套 jsdom 或组件级测试（否决：UI 的价值在布局、像素与手势命中，脱离官方渲染核心的断言证明不了真机行为）
- 用截图基线做整幅视觉回归（否决：样式迭代会造成大面积无意义失败，改用区域指纹与语义断言，只在视觉确有要求处取点比对）

## 影响

- 与硬件无关的缺陷在几秒内就能被发现，且失败信息直接指向文件与行号；每个修过的 bug 留下可重复执行的证据，重构时能立刻判断有没有碰坏行为。代价是测试与实现耦合在若干约定的探针与替身上：新增页面逻辑时要同步维护 pages.ts 与 stub，官方 DevTools 协议的 inspect 行为（整屏调试着色、只在重绘帧返回矩形）需要在用例侧规避；这套测试不覆盖帧率、内存占用与真机时序，真机验收仍然不可省略。
