# 0044 — amiibo 镜像桥接帧上传与 NFC 命令通路软件模拟标签

- 状态: active
- 日期: 2026-09-19
- 替代: 无

## 背景

板卡没有 NFC 前端，主机读取 amiibo 走的是手柄的 Command 0x01 通路（见 [controller-switch2.md](../controller-switch2.md) 的 NFC 章节），
因此只能在软件里扮演一张常驻感应区的 NTAG215 标签：需要决定镜像放哪、怎么从 PC 传进来、以及 Command 0x01 在哪一层实现。
抓包只给出少量样例帧，0x05 无卡形态与 0x15 帧头状态位等细节存在不确定性，实现必须把不确定位收敛到一处，便于真机对账时替换。

## 决策

镜像经桥接帧（新增 0x40-0x43 四类帧，OTA 同构但逐帧回 ACK）上传，
落 **storage 分区（SPIFFS，挂载 /amiibo）的固定槽位文件表**：
`a<i>` 记录 572B = 540 镜像 + 32B 厂商签名、`n<i>` 名称、`sel` 选中号，容量 200 槽，
选中槽位持久化、重启自动恢复；上传接受 540（签名补零）或 572 两种尺寸。
上传会话纯逻辑（amiibo_proto.c）与标签模拟状态机（target/ns2/ns2_nfc.c）都用主机端用例钉住，
ble_session 只做 case 转接。

存储选 storage 分区而非 NVS：读缓冲头区需要厂商签名（572B 记录），NVS 的 24KB 放不下有意义的数量。
初始化走后台任务，不阻塞启动链。

## 考虑的方案

- storage 分区 SPIFFS 槽位文件（采纳：容量大、记录可带签名、NVS 只留设备设置）
- NVS 固定槽位表（放弃：24KB 上限约束槽位数量与 572B 记录尺寸）
- OTA 式窗口流控（放弃：572 字节三帧数据用不上窗口，逐帧 ACK 更简单且天然给出续传起点）
- 纯裸分区自管槽位表（放弃：自管磨损均衡与掉电安全不如直接用 SPIFFS）

## 影响

- 槽位记录 572B，写满 200 槽才报 STORE_ERROR；主机写卡的存档经写回回调落回选中槽位记录的镜像段（签名段不动），跨重启保留。
- 0x05/0x15 的应答体细节与真机不符时只需改标签模拟状态机一处，黄金字节用例同步更新；
  屏幕 UI 的 amiibo 选择页将来直接读槽位表即可。
- 读卡收尾仍差最后一步（主机抽完 600 字节后静默约 3 秒整轮重来，扫值与补发实验全败，外部无先例可抄，
  详见 [controller-switch2.md](../controller-switch2.md) 的读卡流程）；将来拿到真机抓包跑通后应把结论收敛进状态机并撤掉运行时对账开关。
- 读卡收尾未通期间，存储初始化临时停用（槽位操作按「未挂载」拒绝），恢复即解开注释。
