# 0044 — amiibo 镜像桥接帧上传与 NFC 命令通路软件模拟标签

- 状态: active
- 日期: 2026-09-19
- 替代: 无

## 背景

板卡没有 NFC 前端，主机读取 amiibo 走的是手柄的 Command 0x01 通路
（controller.md「NFC 与 Amiibo 数据交互协议规范」），因此只能在软件里扮演一张常驻感应区的 NTAG215 标签：
需要决定镜像放哪、怎么从 PC 传进来、以及 Command 0x01 在哪一层实现。
抓包（ndeadly/switch2_controller_research）只给出少量样例帧，0x05 无卡形态与 0x15 帧头状态位等细节存在不确定性，
实现必须把不确定位收敛到一处、便于真机对账时替换。

## 决策

镜像经桥接帧（新增 0x40-0x43 四类帧，OTA 同构但逐帧回 ACK）上传，
落 **storage 分区（SPIFFS，挂载 /amiibo）的固定槽位文件表**：
`a<i>` 记录 572B = 540 镜像 + 32B 厂商签名、`n<i>` 名称、`sel` 选中号，容量 200 槽，
选中槽位持久化、重启自动恢复；上传接受 540（签名补零）或 572 两种尺寸。
上传会话纯逻辑（amiibo_proto.c）与标签模拟状态机（target/ns2/ns2_nfc.c）都用主机端用例钉住，
ble_session 只做 case 转接。

初版曾选 NVS 12 槽（免文件系统依赖），同日推翻：读缓冲头区需要厂商签名（572B 记录），
NVS 24KB 放不下有意义的数量；storage 分区约 8MB 本就闲置（ADR 0009 预留），
SPIFFS 每文件几百字节开销在 200 槽规模无感。
代价是 CLI 路径的 SPIFFS/VFS fopen 调用链栈深：
remapad-input 与 UART console 两条 CLI 任务栈都提到 8192（首启格式化 8MB 约 40 秒，只发生一次）。

存储初始化曾同步跑在 app_main：首启格式化与逐槽 stat 扫描把启动画面拖黑数秒（用户实测回归），
后改为 amiibo_store_init_task 后台任务 + opendir 单趟扫描（替代 200 次 stat）：
正常路径存储约 1.7 秒就绪，不再阻塞启动链。

## 考虑的方案

- storage 分区 SPIFFS 槽位文件（采纳：容量大、记录可带签名、NVS 只留设备设置）
- NVS 固定槽位表（放弃：24KB 上限约束槽位数量与 572B 记录尺寸）
- OTA 式窗口流控（放弃：572 字节三帧数据用不上窗口，逐帧 ACK 更简单且天然给出续传起点）
- 纯裸分区自管槽位表（放弃：自管磨损均衡与掉电安全不如直接用 SPIFFS）

## 影响

- 槽位记录 572B，写满 200 槽才报 STORE_ERROR；
  0x05/0x15 的应答体细节与真机不符时只需改 ns2_nfc.c 一处（黄金字节用例同步更新）；
  主机写卡的存档经写回回调落回选中槽位记录的镜像段（签名段不动），跨重启保留；
  屏幕 UI 的 amiibo 选择页将来直接读 amiibo_store 的槽位表即可，无需再动底层。
- 换 NFC 读缓冲头区填充形态（结构模板 vs 全零）走 `amiibo hdr 0|1` 运行时开关，不重烧固件即可对账；
  `amiibo done/state/push` 同为真机对账的实验面（收尾状态值与补发应答形态）。
  读卡收尾仍差最后一步（主机抽完 600 字节后静默约 3 秒整轮重来，扫值与补发实验全败，
  外部无先例可抄，详见 controller.md「Amiibo 读写完整交互时序」）；
  将来拿到真机抓包跑通后，应把结论收敛进状态机并撤掉这四个运行时开关。
- 读卡收尾未通期间，存储初始化在 `main.c` 临时停用（省掉挂载与扫描的常驻开销，
  槽位操作按「未挂载」拒绝），恢复即解开注释。
