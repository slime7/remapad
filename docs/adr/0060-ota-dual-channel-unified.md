# 0060 — OTA 升级统一为串口与 WiFi 双通道共用一套协议与状态机

- 状态: active
- 日期: 2026-09-30
- 替代: 无

## 背景

OTA 原先只走 USB-Serial/JTAG：UDP 的 netlog 调试通道上 OTA 帧被设备端直接丢弃，host 模式下没有串口时设备无法升级。
桥接帧协议本身已是分块加窗口 ACK 的形态（200 字节一帧、16 帧一窗、序号续传），缺的只是 UDP 丢包下的重发节奏与设备端对重复帧的语义。

## 决策

串口与 WiFi 共用同一套 OTA 协议帧、PC 端状态机与固件会话核心，不另做网络专用实现。
固件 netlog 收到的 OTA 帧走 ota_link 同一适配进会话核心，ACK 按在位通道双路回发；
接收中的同尺寸 BEGIN 与收完后的 END 按幂等应答，会话核心不重入预擦与校验。
PC 端 OtaJob 按「链路会丢包」设计：BEGIN 与 END 周期重发，窗口应答等待 1.2 秒、
设备 5 秒空闲作废后自动从头重来（限 3 次），迟到的旧应答只前进不回卷；UDP 大写入按 1 KB 分片免 IP 分片。
UDP 上收尾应答彻底没等到时按不确定完成收场、由 --wait 或重连后的 version 确认，串口维持硬失败；
截图与 amiibo 上传保持串口专属。

## 考虑的方案

- 为 UDP 单独做一套分块传输（否决：与既有 OTA 协议形成两套并行维护，丢包语义也没有比窗口重发多出收益）
- 把 netlog 通道改成 TCP 或加自定义确认层（否决：netlog 的定位是轻量调试通道，改承载协议牵动日志、CLI 与网络手柄三条既有用户）
- 逐帧 NACK 替代整窗重发（否决：设备端与 PC 端都要新增状态，收益只在高丢包率下明显，调试场景不值得）

## 影响

- 正面：host 模式（唯一 Type-C 让给手柄）下设备也能升级，远程排障的恢复链路闭合；串口与 WiFi 行为一致，升级代码只有一份。
- 正面：BEGIN/END 幂等让串口上的日志挤占应答同样获得兜底，不需要为两种链路调不同参数。
- 成本：WiFi 升级比串口慢（整窗重发为粒度），升级完成后设备重启、netlog 会话要手动重开；UDP 上存在收尾应答全丢的极小概率路径，只能靠事后 version 确认。
- 限制：截图与 amiibo 上传仍只走串口；该通道是局域网内无鉴权明文，WiFi 升级只在可信网络里用。
