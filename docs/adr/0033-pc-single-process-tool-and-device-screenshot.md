# 0033 — PC 侧工具合并为单进程会话并新增实机截图通路

- 状态: active
- 日期: 2026-09-15
- 替代: 无

## 背景

PC 侧原本有三个脚本（bridge.py / uartctl.py / ota.py），各自独占打开同一个 USB-Serial/JTAG 口：link.py 的 CreateFileW 共享模式为 0，桥接运行期间第二个进程只能拿到端口占用错误。固件侧 input/input_link.c 早已按帧头把字节流分成桥接帧与 CLI 文本，缺的是 PC 侧只有一个持有者。实机调试还缺一条看到屏幕的路径：触摸预览页跑在浏览器里，渲染核心是官方 wasm，看不到本机渲染加速器与面板路径的实际结果，而渲染管线只保留三条 32 行条带缓冲、面板是只写 SPI（无 MISO，读不回 GRAM）。

## 决策

PC 侧合并成一个进程 pc/remapadctl.py：同一个会话循环里做手柄转发、串口命令行、实机截图与固件 OTA，串口句柄只此一处；link.py 继续作为唯一的串口与帧编解码实现。桥接协议新增设备到 PC 的截图帧 IMAGE_INFO（0x21，宽 u16 小端 + 高 u16 小端 + 格式）、IMAGE_DATA（0x22，偏移 u32 小端 + 最多 200 字节像素）、IMAGE_END（0x23，总字节数 u32 小端），完整性按偏移覆盖满整幅画面判定。固件新增串口命令 shot：PocketJS owner task 在下一帧把当前画面按整屏重渲染一遍（与面板同一条渲染路径），逐条带回传，单块等待上限 200 ms，超时中止。PC 侧按偏移拼齐后写 PNG（标准库 zlib + struct，不引入新依赖）。

## 考虑的方案

- 保留三个脚本，靠共享句柄打开端口（否决：串口是多读端竞争的单 FIFO，命令回复可能被桥接进程读走，回归断言不再可重复；uartctl 也不解帧，桥接跑起来就会看到二进制乱码）
- 把截图需求交给触摸预览页或官方 playground（否决：两者都是浏览器渲染，覆盖不到本机渲染加速器与面板提交路径，看不出实机差异）
- 面板 GRAM 回读（否决：这条板级通道是只写 SPI，没有 MISO）
- 截图期间停掉 UI 或单独开一个截图任务（否决：整屏重渲染本来就在 owner task 上，另起任务要复制渲染器与帧的所有权）

## 影响

- 正面：桥接运行期间命令、截图与升级同时可用，PC 侧只剩一个串口持有者；实机画面能落成文件，与预览页逐像素对照不再靠人眼描述。
- 成本：截图那次整屏重渲染会让 UI 冻结约 0.2 到 1 秒（BLE 输入在另一个任务上，不受影响）。
- 限制：设备到 PC 的图像分块用等待式发送，PC 侧没在读时会中止本次截图并只在串口日志里留一行原因。
