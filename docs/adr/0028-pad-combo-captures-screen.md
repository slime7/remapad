# 0028 — 手柄组合键捕获为屏幕操控：方向键移动焦点、圆圈键确认

- 状态: active
- 日期: 2026-09-15
- 替代: 无

## 背景

手柄输入此前只有一条去向：解析成私有格式后编码给目标主机。板上屏幕是触摸屏，没有实体按键也没有遥控器，主机在跑游戏时用户想改设置只能放下手柄去点屏幕；两端都在手上时，手柄本来就有十字键与面键，却一点也用不到屏幕上。

## 决策

数据面按私有按键位识别组合键 L1+R1+L3+R3（四键同时按住 300ms 才翻转）：命中后板子捕获输入——那一刻先补一帧全松开，其后按原来的上报节奏续发同样的中性帧（玩家输入不再上行，同时不让主机把手柄判成离线），转为把十字键与圆圈键映射成 PocketJS 按键位交给 UI——方向键按显示顺序移动焦点，圆圈键经框架的 onPress 等价于点屏幕；再按一次组合、同样按住阈值后退出，恢复转发。捕获状态由 dp/dp_ui.c 维护（dp_task 写、PocketJS owner task 读）。UI 侧把每个页面与底栏的 focusable 绑在「自己是当前页、且没有弹窗盖住」上（App.tsx 的 interactive 往下传，hooks/usePadControl.ts 只管操控窗口与「非操控状态不留焦点环」），框架的遍历清单因此只含画面上的控件——七个页面在首帧就已全部挂载，静态的 focusable 会把隐藏页的控件留在名单里；可滚动页再把可聚焦行的位置表交给 usePageScroll，焦点走到下方时页面跟着滚，选中项不会被底栏挡住。

## 考虑的方案

- 组合键在私有格式层判定、不逐布局登记（采纳）：家族表只负责把 L1/R1/L3/R3 放到私有键位，四键同时按住即命中，既有布局与将来的新手柄都自动可用
- 逐布局登记组合键（否决）：同一件事要在各家族的布局行里各写一份，新增手柄容易漏配，闸门语义也会各不相同
- 用单一功能键（如 Home 长按）触发（否决）：游戏里这些键太常用，误触代价高；组合键本身就要按需求做得足够复杂
- 捕获期间彻底静默（否决）：主机的按键状态停在最后一份报文上，正按着的键会一直按在主机那头；而且主机按稳定不跳号的上报流判断链路健康，整段停发会被判成手柄离线。改为补一帧全松开、捕获期间续发中性帧
- 为布局表新增一套 debug 布局（否决）：调试注入本来就接在私有格式层，`dp/dp_source.c` 的键名表直接按 `PAD_BTN_*` 注入，`key ui` / `key up` / `key a` 已经等价于「不插手柄直接发私有按键码」，再加一套布局只会多一份要跟着维护的映射
- 让固件代管焦点（否决）：焦点与激活语义属于 UI 层，固件只该交付按键位；屏幕上的控件清单每加一个页面就变，固件里放一份必然过期

## 影响

- 正面：不插手柄也能验证——uartctl 的 `key ui` 注入同一组合键，进去以后用 `key up` / `key right` 与 `key a` 操作界面，UI 调试页也有入口；判定在数据面，桥接 PC 与 USB host 直插两条输入路径同样可用。
- 正面：焦点环由原生核心套用 `focus:` 变体，不占每帧 JS；圆圈键与触摸点按汇入同一个 onPress 入口，两种输入不会各走一套激活逻辑。
- 约束：host profile 因此声明 `input.buttons`（应用侧仍是 enhances），点得动的新控件要自己带上 focus: 环，否则手柄操控时看不到焦点落在哪。
- 约束：框架的遍历对 hidden 无感知，可见性过滤只能留在应用侧——新增页面要把 focusable 绑到 App 传下来的 interactive()；可滚动页新增可聚焦行时，要把行位置加进 usePageScroll 的 focusRows，否则焦点走到下方时看不到选中项。
- 约束：进入模式会先向主机补一帧全松开，捕获期间继续按 15 ms 的上报节奏续发同样的中性帧；主机侧看到的是「按键松开、摇杆回中」的静态状态，直到退出模式才恢复真实输入。
