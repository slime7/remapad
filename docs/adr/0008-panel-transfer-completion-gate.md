# 0008 — 面板提交增加传输完成门控

- 状态: active
- 日期: 2026-09-12
- 替代: 0007

## 背景

实机排查发现 UI 页面切换与滚动时部分区域偶发黑线或错位内容。esp_lcd 的 draw_bitmap 只把 CASET/RASET 命令与颜色分块的 DMA 事务排队即返回，官方约定颜色缓冲必须在 on_color_trans_done 之后才能复用；而 0007 确立的 strip 提交让所有 damage region 复用同一 PSRAM 缓冲，panel_transfer 返回后宿主立即 memset、渲染并字节交换下一块区域。40 MHz SPI 下 DMA 读 PSRAM 约 5 MB/s（整帧约 27 ms），CPU 改写一旦赶上飞行中的 DMA，面板读到的就是清零像素或下一区域内容。经核对 IDF v6.1 源码，spi_device_release_bus 并不等待排队事务，排空发生在下一次 draw 内部，因此 panel.c 原注释的"复用同一缓冲是安全的"假设不成立；多区域与整帧重绘（页面切换、滚动重叠）竞态窗口最大，表现为偶发黑线。

## 决策

panel_transfer 在 esp_lcd_panel_draw_bitmap 返回后，以 on_color_trans_done 回调（ISR 释放二值信号量）等待最后一笔颜色分块传输完成后才返回，超时 200 ms 按传输失败处理并由调用方 abort 丢弃整帧；回调在面板 IO 创建时随 io_config 注册。该决策部分取代 0007 中 strip 提交的颜色缓冲复用语义：缓冲必须待传输完成门控后才能改写；0007 的 esp_lcd 内置 ST7789 驱动选型、初始化参数、触摸与背光范围继续有效。

## 考虑的方案

- trans_done 回调加二值信号量完成门控（采用）：单缓冲即可保证正确，与官方颜色缓冲生命周期约定一致，改动收敛在 panel.c
- 双 strip 缓冲乒乓，仅在重用前等待：保留渲染与传输重叠，但整帧缓冲要多占约 130 KB PSRAM，且修复黑线并不需要
- 复制到内部 RAM 的 DMA 缓冲再提交：绕开 PSRAM 直读，但内部 RAM 拿不出整帧容量，且每帧多一次拷贝
- 沿用无门控提交，依赖下一次 draw 的 acquire 排空：排空发生在缓冲改写之后，正是实机黑线根因，放弃

## 影响

- 正向：实机黑线与错位内容根因消除，颜色缓冲生命周期符合官方约定，内存占用与缓冲布局不变。
- 代价：渲染与面板传输串行化，整帧重绘在 40 MHz 下最多增加约 27 ms 串行等待，整帧动画对 60 Hz tick 的预算压力上升；若日后整帧动画掉帧，再评估双缓冲乒乓方案。
